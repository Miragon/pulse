# Parity with the MCP cockpit

Pulse shows an engine in two UIs: the cockpit of the MCP server, a card in an AI chat, and the
panels of this extension, tabs next to your models and code. They share a core up to building
blocks, not their screens: Pulse's UI foundation (the words for a count, the tone of a situation,
how a date, a duration, a count or an id reads, the Miragon tokens and the brand gates:
`@miragon/pulse-ui/format`, `/tones` and `/testing`), the engine rules of `@miragon/pulse-c7-core`,
the numbers of a feature both show (boards first: one builder over one read; elsewhere each tool
keeps its numbers behind the same words until its view moves onto shared ones) and building blocks
that take props and callbacks only. Each keeps its own screens and host wiring. The cockpit is
React on `@miragon/pulse-ui`; the extension's webview moves from Preact to React on pulse-ui in
one switch and shares one compact look with the cockpit. The product owner decided so on
2026-11-12 (`apps/vscode/docs/adr/ui-foundation.md`, D1 to D9).

Six cockpit views have a counterpart here: the engine overview, a process, its instances, an
instance, an incident and the history. This page lists every difference between them, so that each
one is a choice and not an accident.

## How to read it

- **Origin.** _host_: what the surface forces, a chat card (a height budget, hand-offs to the chat,
  a model that reads the view) or an editor tab (your models and code, native dialogs and
  documents, live updates). _engine_: what only Camunda 7's REST API offers and the extension's
  engine-neutral contract leaves out. _decided_: a record says so, named in the row: _contract_ is
  `apps/vscode/docs/adr/runtime-contract.md`, _UI_ `apps/vscode/docs/adr/user-interface.md`,
  _writes_ `apps/vscode/docs/adr/writes.md` with `apps/vscode/docs/adr/migrations.md`, _boards_
  `apps/vscode/docs/adr/boards.md`, _CLAUDE.md_ the repository's rules (a process view spans every
  version of its key). _history_: it grew on one side, no record holds it.
- **Status.** _closed_: both tools agree now and a test keeps them so. _wanted_: it stays different,
  since each tool follows its audience; a history row stays until a pair feature closes it (the
  rule below). _open_: a gap one tool should close.

## A new pair feature

A change that adds or changes what one of the six views shows or does (a field, a count, an action)
is a pair feature. Its pull request:

1. Says whether the other tool gets it too. Built on one side, it adds or updates its row here;
   built on both, it closes its row or updates it.
2. Takes the foundation: the words of `COUNT_TERMS` and `PRODUCT_GLOSSARY`, the tone from
   `SITUATION_TONES`, every date, duration, count and id from `@miragon/pulse-ui/format`.
3. Builds its content with props and callbacks only, no host context (no `useToolQuery`,
   `ConfirmDialog`, `HandOffButton` or `HostBridge`), as
   `packages/connectors/engine/engine-connector/src/widgets/process-definitions-table-view.tsx`
   (`renderActions`) and `history-steps.tsx` beside it do. Where both tools show it, a shared
   building block is the default, on React: the cockpit renders it now, the webview from its switch
   to React on pulse-ui (D9) on; until that switch, each tool builds its own. A feature that moves
   onto shared numbers (boards first) takes them from one builder over one read. A primitive goes
   into `@miragon/pulse-ui`, an engine block into a shared package, created with the first one both
   tools render; until then the cockpit keeps its content in the connector.
4. Changes a decided row only together with its record.

No gate tells a wanted difference from a forgotten one: the reviewer holds the diff to this page.
