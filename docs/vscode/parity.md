# Parity with the MCP cockpit

Pulse shows an engine in two UIs: the cockpit of the MCP server, a card in an AI chat or a page of
its web app, and the panels of this extension, tabs next to your models and code. They share a core
up to building blocks, not their screens: Pulse's UI foundation (`@miragon/pulse-ui/format`,
`/tones`, `/testing`), the engine rules of `@miragon/pulse-c7-core`, the numbers of a feature both
show (boards first: one builder over one read; elsewhere each tool keeps its numbers behind the same
words until its view moves onto shared ones) and building blocks that take props and callbacks only.
Both are React on `@miragon/pulse-ui` in one compact look since the webview left Preact
(2026-11-14), and each keeps its own screens and host wiring. The product owner decided so on
2026-11-12 (`apps/vscode/docs/adr/ui-foundation.md`, D1 to D9), and D10 on 2026-11-19: the web app
gets a frame and screens of its own in this extension's style, from the blocks the extension renders
over the same builders, with the cockpit's operations views embedded; the chat keeps its cockpit.
Until a screen lands, a row's cockpit is the chat's and the web app's, and its step updates the
rows. Six cockpit views and a board have a counterpart here: the engine overview, a process, its
instances, an instance, an incident, the history. Every difference is listed, none an accident.

## How to read it

- **Origin.** _host_: what the surface forces, a chat card (a height budget, hand-offs to the chat,
  a model that reads the view) or an editor tab (your models and code, native dialogs and
  documents, live updates). _engine_: what only Camunda 7's REST API offers and the extension's
  engine-neutral contract leaves out. _decided_: a record says so, named in the row: _contract_ is
  `apps/vscode/docs/adr/runtime-contract.md`, _UI_ `apps/vscode/docs/adr/user-interface.md`,
  _writes_ `apps/vscode/docs/adr/writes.md` with `apps/vscode/docs/adr/migrations.md`, _boards_
  `apps/vscode/docs/adr/boards.md`, _foundation_ `apps/vscode/docs/adr/ui-foundation.md`,
  _CLAUDE.md_ the repository's rules (a process view spans every version of its key). _history_: it
  grew on one side, no record holds it.
- **Status.** _closed_: both tools agree now and a test keeps them so. _wanted_: it stays different,
  since each tool follows its audience; a history row stays until a pair feature closes it (the
  rule below). _open_: a gap one tool should close. _decided 2026-11-19_: a record changed the row,
  and the step it names lands the change; until then the row says what each shows today.

## A new pair feature

A change that adds or changes what one of the six views shows or does (a field, a count, an action)
is a pair feature. Its pull request:

1. Says whether the other tool gets it too. Built on one side, it adds or updates its row here;
   built on both, it closes its row or updates it.
2. Takes the foundation: the words of `COUNT_TERMS` and `PRODUCT_GLOSSARY`, the tone from
   `SITUATION_TONES`, every date, duration, count and id from `@miragon/pulse-ui/format`.
3. Builds its content with props and callbacks only, no host context (no `useToolQuery`,
   `ConfirmDialog`, `HandOffButton` or `HostBridge`), as `process-definitions-table-view.tsx`
   (`renderActions`) and `history-steps.tsx` of the cockpit's widgets do. Where both tools show
   it, a shared building block on React is the default (D9), shared numbers come from one builder
   over one read (boards first). A primitive goes into `@miragon/pulse-ui`, an engine block into
   `@miragon/pulse-blocks` (the tiles, an engine's process list, an instance's, a process's), which
   takes each tool's table, id, link, diagram and writes as slots, in one row convention (Rows above).
4. Changes a decided row only together with its record.

No gate tells a wanted difference from a forgotten one: the reviewer holds the diff to this page.
