# Widget host simulation (`pnpm --filter @miragon/pulse-mcp-server test:host`)

Playwright gate for the **built** widget bundle, run in CI as "Widget host
simulation (test:host)". It renders exactly what an MCP Apps host renders:

- `global-setup.ts` boots the real composition root (`createApp` from
  `src/app.ts`, default read-only deployment, plus a `engine:operations`
  one for the write scenario, one whose second profile the server refuses,
  its secret's variable unset, at `HOST_SIM_REFUSED_URL`, one with the board files of
  `fixtures/boards` at `HOST_SIM_BOARD_URL`, one with a single engine beside a board,
  `fixtures/one-engine-boards`, at `HOST_SIM_ONE_ENGINE_BOARD_URL`, and one with the stub beside
  a loopback Camunda 8 cluster under two profiles of the client credentials grant and the board of
  `fixtures/camunda8-boards` over the stub and one of them, at `HOST_SIM_CAMUNDA8_URL`) serving
  `dist/mcp-app.{js,css}`, a CIB seven REST stub (`stub-engine.ts`,
  `fixtures/process-definitions.json` with their statistics and no open incident, the `invoice`
  diagram `fixtures/invoice.bpmn` with two instances at `approveInvoice` and twelve started in
  the last 30 days in its history, sixteen failed jobs, their backlog counts, one invoice instance
  with two open incidents that only its own reads see; under
  `/realistic`, real-sized data in `realistic-engine.ts`) and the host's
  server side (`host-backend.ts`, a real MCP client), all on ephemeral
  loopback ports. A scenario can hold the stub's answers to one search term
  and release them later (`POST /__control/hold|release?term=<term>` at
  `HOST_SIM_ENGINE_URL`; `GET /__control/waiting?term=<term>` says how many
  wait), so an in-flight state is asserted without a timing window. The Camunda 8 cluster
  (`c8-engine.ts`, on the server tests' loopback engine `test/engine-goldens/fake-c8-cluster.ts`)
  answers a board's reads on 8.9, keys of 16 to 19 digits and the Zeebe diagram
  `fixtures/order.bpmn` as text, its token endpoint at Keycloak's path on the same origin; it
  records what it was asked (`GET /__control/requests` at `HOST_SIM_C8_ENGINE_URL`, `DELETE`
  forgets).
- `host-sim.html` is a minimal SEP-1865 host. It reads the view resource
  (`resources/read` of the tool's `_meta.ui.resourceUri`: `ui://views/<tool>.html`,
  the inline document the boot serves, or a module's own), renders it as `srcdoc`
  in a `sandbox="allow-scripts"` iframe
  under the CSP built from the resource's `_meta.ui.csp`, answers
  `ui/initialize`, and proxies every `tools/call` the view makes to the server.
- A scenario can size the frame (`width=<px>`; default 960): the layout
  scenarios render at the 760 px a chat gives an inline view.
- The rendering tool is the real `engine_open_cockpit` against the stub,
  opened on its overview unless a scenario names a `view` (the jobs, a process
  for the BPMN scenario, the instances on the realistic engine for the
  in-widget query; the write one: the failed jobs on the operations
  deployment), so the view gets the server's real `structuredContent` and data
  shape (the view picked by the name its document's prelude sets).

**The cockpit's chrome inline.** Every scenario of the engine module renders the cockpit, whose head
(sections, engine switch, Refresh) sits above the route. Inline the head is the only row: a
drilled view's breadcrumb takes the sections' place, a head section shows none. Under the compact
look (28 px heads, 28 px rows with their 24 px row actions, a view's header its 40 px bar) a
600 px budget then shows eleven of the sixteen job rows (575 px with the Load more button; a
twelfth would need 3 px more) and all three of the overview's definitions at 960 px and at 760 px
(456 px); a host's line above the view (a recovered render's "Reloaded at", the fullscreen
toggle's bar) adds 40 px and still leaves room for all three (496 px), and under it a 490 px
budget fits exactly one at 960 px (484 px with its footer; two rows and the footer are 512 px,
more than all three). A cut pays for the footer it adds ("1 of 2 shown"): where the rows it would
hide do not, the fit cuts nothing and the view scrolls, so an instance's two incidents both show
in 600 px. The host scenarios pin each count. The width refit (`inline-fit.spec.ts`) and the row
menu run at 800 px, where all sixteen jobs fit (706 px).

Height checks read the **settled** report, the one equal to the document's current
max-content height: auto-resize reports one frame late, so right after the content becomes
visible the last report can still be an earlier state's (the view's loading state).

**Pinned scenarios** assert the CURRENT behaviour of a known defect outside
this repo's fix scope. They fail on purpose once the fix lands: flip them to
the expected behaviour named in their assertion message.

Run it after `pnpm build` (the server imports the workspace packages' dist):

```bash
pnpm --filter @miragon/pulse-mcp-server exec playwright install chromium   # once
pnpm --filter @miragon/pulse-mcp-server test:host                          # builds the UI, then tests
```

Not part of `pnpm test` (needs the Vite bundle and a browser). Run it locally for
any change to the widget shell, pulse-ui, `src/ui/` or the `@modelcontextprotocol/ext-apps` pin.
Failed scenarios leave a trace and a screenshot in `apps/mcp-server/test-results/host/`
(`pnpm exec playwright show-trace <zip>`).

## The web app on the real server (`pnpm --filter @miragon/pulse-mcp-server test:web`)

`web/` is a suite of its own, run in CI as "Web app (test:web)": the page of apps/web as a browser
reaches it, its own config (`web/playwright.config.ts`, which this suite's config ignores) and
global setup. `test:web` builds the view bundle and apps/web first; `web/global-setup.ts` boots the
real composition root (`createApp`) under OAuth, so with the operations toolset, with the web app
on (`MCP_WEB_DIR` on `apps/web/dist`, never the package's `web/`, which only the image fills) at
`http://localhost:<port>`, its `MCP_URL`, where Chromium keeps the `__Host-` cookies of plain http.
Each deployment signs in through a fake identity provider of its own
(`@miragon/pulse-widget-shell/testing/oidc`: Keycloak's paths, a login page with a link per user,
the web client's callback and post-logout URIs exactly) over this suite's stub engine: `main` with
the stub and the broken engine, the board files of `fixtures/boards` and access tokens of 300 s
(`WEB_SIM_URL`), `short` with the stub alone, no board and access tokens of 5 s, which the server
renews before each call (`WEB_SIM_SHORT_URL`), `adfs` like `short`, its provider the fake's ADFS
flavor behind the generic OpenID Connect provider (`MCP_OAUTH_OIDC_ISSUER`, the caller in `sub`
by its issuance rule; `WEB_SIM_ADFS_URL`), `camunda8` with the stub, the host simulation's
Camunda 8 cluster under two profiles and the board of `fixtures/camunda8-boards`
(`WEB_SIM_CAMUNDA8_URL`). The
workers read what a provider recorded through `WEB_SIM_CONTROL_URL` (`web/web-sim.ts`), each
refresh token named with its session and each token request with its resources; a scenario reads
only its own browser's session (the `session_state` its sign-in returned), and ends it at the
provider by the provider's cookie, or ends its grant through the control, never another's. The chat's Retry and Edit on the same instance, the positive half of `page.spec.ts`'s
writes, are this suite's (`compact-frame.spec.ts`).
